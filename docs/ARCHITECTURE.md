# Fitura+ architecture

This repository began empty. Fitura+ is a modular Next.js App Router application with React, TypeScript, Prisma and Zod. The web client calls a same-origin JSON API. Session secrets are hashed in the database; passwords use scrypt. Business access rules run on the server for every operation. Client records require an accepted, explicit sharing relationship. Admin accounts cannot be self-registered.

## Persistence and deployment

SQLite is the runnable development database, with committed Prisma migrations and original seed content. It also supports a single-instance container with a persistent volume. PostgreSQL migration is a deployment task, not a claimed active integration: change the Prisma datasource, regenerate migrations for PostgreSQL, and run the security/concurrency test suite before multi-instance deployment. SQLite serializable transactions prevent conflicting appointments in this release. Session and rate limit records are shared by requests through the database.

## Boundaries

Auth / profiles / coaching relationships / exercise library / programs and sessions / foods and diary / recipes and meal plans / progress / appointments / messaging / subscriptions / audit. Related models use foreign keys, ownership indexes, and cascade deletion where appropriate. Library entries are retained; personal entries are deleted with the account. Audit entries contain event metadata, never passwords or health payloads. Exports contain personal records only. Coach exports do not copy client health data.

## Integrations

AI runs through a server-only provider adapter and requires an API key, explicit user consent, and human confirmation. It never writes plans. Nutrition seeds are original illustrative estimates, not a verified commercial database. Stripe checkout/portal and signed webhooks, and Resend password-recovery adapters are implemented but disabled without credentials. They require provider test-mode validation before rollout. WhatsApp, push, wearables, external food search, image recognition and calendar sync remain unimplemented and unavailable. No simulated delivery or billing success. Marketplace is off by default. These are not production-complete integrations.

## Safety and operational limits

No generated weight-loss targets. Onboarding records adult/youth status; youth AI requests are disabled. General fitness assistant is informational, not medical care. Health records private by default. Production deployment requires TLS, backups and restore verification, email verification, retention/legal review, penetration testing, monitoring and a durable jobs service for delivery retries. The feature report records the exact implementation scope.

## Exercise catalog and daily activity

The catalog retains 2,066 pinned Free Exercise DB/Flow records and stable fe_/fl_ IDs. Search aliases, muscle filters and pagination run locally on the server. Library responses merge the catalog with saved exercises. Demonstration resolution uses only the checked-in SmartWorkout animation URL index (1,029 entries), with normalized word-order/alias matching and direct sw_ category/slug IDs. Every one of the 1,029 indexed paths is reachable in the demonstrated catalog (1,086 entries including legacy equivalents). New source-native entries include instructions and bundled Hebrew translations. Thumbnails and MP4s are hosted by SmartWorkout; unmatched legacy entries remain resolvable for saved plans but are excluded from new catalog/builder choices. Library responses contain only demonstrated exercises. Saved routine displays, generated workouts and new sessions also exclude unsupported movements, while finished history remains intact. Saves and imports reject unsupported exercises. The demonstration endpoint resolves saved names as well as canonical IDs. The player supports pause/play, page visibility and reduced motion; errors offer retry with no cross-provider fallback. Source links and captions are absent from the player. Older media files and licenses remain archived. The 2,066 Hebrew translation records are generated at build time from public text and polished through a maintained terminology glossary. No user data is sent for translation; no translation network request occurs at runtime. State and library serialization repairs older catalog records that copied English into Hebrew fields. Previously saved unmatched provider exercises retain instructions. CardioActivity and DailySteps are private user-owned records. Daily steps upsert by user/date; imported workouts upsert by user/source/external ID. The mobile WebView bridge accepts explicit fitness-sync requests only from the authenticated activity route, reads aggregate steps and completed aerobic workouts through HealthKit or Health Connect, and returns a request-scoped result. The web page validates consent/request/account identity before posting to the current session. No background collection, health-platform writes or raw step samples are implemented.
